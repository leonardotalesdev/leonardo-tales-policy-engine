## Summary

v0.2.0 adds a separate controlled Action Policy evaluation surface while preserving the original generic `evaluatePolicy()` semantics. This is a backward-compatible additive API. Package version 0.2.0 and action profile contract tales-actions-v1 are separate concepts; a package version does not confer runtime authority or prove publication.

The private root `policy-engine-workspace` remains version 0.1.0. Only the actual distributable package version changes; dependencies and lockfile remain unchanged.

## New API

- `evaluateActionPolicy()`
- `ACTION_PROFILE_VERSION = 'tales-actions-v1'`
- Immutable `REGISTERED_ACTION_PROFILES`
- Associated types: `ActionProfile`, `ActionEnvironment`, `ActionExecutionState`, `ActionPolicyBaseInput`, `ActionApprovalContext`, `PendingActionNotificationFacts`, `MeetingReconciliationFacts`, `ActionPolicyEvaluationInput`, and `ActionPolicyEvaluationResult`.

## Registered profiles

Exactly three profiles are registered:

- `telegram.notify_pending_action`
- `calendar.create_meeting`
- `calendar.read_meeting_for_reconciliation`

No wildcard, caller-defined profile, dynamic registration or arbitrary tool permission exists.

## Decision boundary

Every profile first requires valid input, the exact contract/profile, production context, enabled runtime, an authorized target, no secret material in the evaluated payload, no financial/legal/health data, and minimized real user data. Malformed input, unknown profile/version/environment and failed global gates block. Every result requires audit; allow/requires-approval are high risk and blocks are restricted.

| Profile | Decision after global gates pass |
| --- | --- |
| `calendar.create_meeting` | Missing approval: `requires-approval`. Valid bound approval: `allow`. Invalid, mismatched or expired claimed approval: `block`. |
| `telegram.notify_pending_action` | Only a pre-authorized minimized notification for an existing pending action and a runtime-bound recipient can allow. Any failed notification fact blocks; no recursive per-notification approval. |
| `calendar.read_meeting_for_reconciliation` | Only the bound deterministic event of a linked, previously authorized `execution_unknown` execution can allow. Matching execution target, action-bound external ID and `bound_execution_only` scope are required. Other states/scopes block; no new per-action approval. |

Meeting approval must include runtime-verified approver authorization and exact action ID, revision, normalized payload hash, target and profile-version bindings, with unexpired approval. Claimed invalid approval is not treated as missing approval. Reconciliation provides no general event read, Calendar listing or availability lookup.

## Existing evaluator

`evaluatePolicy()` v0.1 semantics remain unchanged. Generic production, deployment, external integration, real user data, secrets, financial/legal/health data and restricted-tier/risk requests remain blocked according to that evaluator, even with `humanApprovalPresent=true`. The new API neither routes nor relaxes the old evaluator.

## Security boundary

Policy Engine:

- does not execute tools;
- does not call Google Calendar;
- does not call Telegram;
- does not authenticate an admin;
- does not read credentials;
- does not access Redis;
- does not grant execution authority.

An `allow` decision is an evaluation result only. The trusted caller supplies verified facts and owns authentication, exact approval verification, OAuth, managed credentials outside the payload, idempotency, state transitions, execution and audit persistence. Model/visitor assertions cannot substitute for those runtime facts. The canonical Constitution is unchanged.
