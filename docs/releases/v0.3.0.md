## Generic evaluation and compatibility

`evaluatePolicy()` applies these inclusive limits before inspecting risk hint indices.

| Field | Inclusive maximum |
| --- | ---: |
| `title` | 256 UTF-16 code units |
| `description` | 4096 UTF-16 code units |
| `requestedAction` | 1024 UTF-16 code units |
| `riskHints` | 32 entries |

Previously accepted oversized inputs now return the complete malformed-input result. The decision is `block`, the risk level is `restricted`, and the only violation is the blocking `invalid-policy-input`. Approval requirements are empty, `auditRequired` is true, and the reason and boundary notes are the standard invalid-input diagnostics. Any overflow rejects the entire input before the policy rules run.

Strings use JavaScript `.length`. Empty and whitespace-only text remain valid. Every entry in an accepted hint list is validated. A malformed entry following a `restricted` hint invalidates the whole list. Empty lists and duplicate hints remain valid, and reordering hints preserves their risk classification.

Generic diagnostics omit caller-controlled free text across `allow`, `requires-approval`, valid policy blocks and invalid-input blocks. Consumers that parsed a title or requested action from those diagnostics should use the structured decision, violation IDs and approval requirements.

The exported `corePolicyRules` and `policyEngineBoundaryNotes` arrays and every exported rule object are frozen at runtime. Their TypeScript declarations are readonly. Consumers that previously wrote to these exports or required mutable arrays should accept readonly inputs or copy the arrays and any rule objects they intend to edit. Evaluation results, their arrays and their records remain mutable and isolated between calls.

These changes to accepted inputs, diagnostic contents and public metadata mutability justify a pre-1.0 minor version increment. Upgrading from v0.2.1 can require caller changes even though the evaluation functions and result fields keep their existing signatures.

## Preserved policy behavior

For valid in-limit generic inputs, structured policy facts determine the same decisions and audit flags. Blocking violations take precedence over pending approvals, and pending approvals take precedence over `allow`. Generic evaluation ignores extra root fields without reading their values.

The independent `evaluateActionPolicy()` contract keeps exact root and nested schemas, rejects unknown fields and retains `tales-actions-v1` with all three registered profiles.

- `telegram.notify_pending_action`
- `calendar.create_meeting`
- `calendar.read_meeting_for_reconciliation`

## Security boundary

Both APIs evaluate supplied facts. The caller owns authentication, fact provenance, approval verification, enforcement, execution and audit persistence. The host must limit request bytes at ingress before parsing. JavaScript proxy traps can run caller code during inspection, and checking the exact keys of a malformed action record can take work proportional to its width. The field limits provide no absolute CPU, heap or wall-clock guarantee.
